Промпт для разработки серверной части Garage Raspberry

Ты — опытный Python-разработчик. Необходимо реализовать серверную часть проекта Garage Raspberry для эмуляции управления гаражными воротами. Сервер должен соответствовать приведённому ниже описанию и взаимодействовать с уже существующим Android-клиентом GarageControl через REST API.

Серверная часть разрабатывается отдельно от Android-приложения. Не нужно разрабатывать Android-клиент, физическое подключение Raspberry Pi или реальное управление GPIO через оборудование. GPIO в текущей реализации эмулируется с помощью команд в терминале и HTTP-запросов.

1. Технологии и структура

Используй Python и FastAPI для реализации REST API. Для запуска сервера используй Uvicorn. Для описания и проверки входных данных используй Pydantic.

Основной файл приложения — main.py. Зависимости должны указываться в requirements.txt. Инструкция по установке и запуску должна находиться в README.md.

Сервер должен запускаться на Linux, в виртуальной машине или Windows без физической Raspberry Pi.

Команда запуска из папки server:

uvicorn main:app --host 0.0.0.0 --port 8000

2. Состояния гаражных ворот

Сервер должен поддерживать четыре состояния ворот:

1 — Закрыта.
2 — Закрывается.
3 — Открывается.
4 — Открыта.

Начальное состояние ворот — закрыта. Начальное состояние блокировки — выключена.

При открытии состояние меняется на «Открывается», а через 4 секунды автоматически становится «Открыта».

При закрытии состояние меняется на «Закрывается», а через 4 секунды автоматически становится «Закрыта».

Завершение движения должно проверяться при обращении к API, без необходимости создавать отдельный фоновый процесс движения ворот.

Сервер должен хранить текущее состояние ворот, состояние блокировки, целевое состояние движения, время начала движения и продолжительность движения в оперативной памяти.

Для синхронизации доступа к состоянию и журналу событий используй потокобезопасную блокировку.

3. REST API

Реализуй следующие HTTP-эндпоинты.

GET /

Возвращает информацию о сервисе, адрес документации API и адрес эндпоинта получения статуса ворот.

GET /api/door/status

Возвращает JSON с полями status_code, status_text и lock_enabled.

Пример ответа:

{"status_code": 1, "status_text": "Закрыта", "lock_enabled": false}

Поле status_code содержит числовой статус ворот. Поле status_text содержит текстовое описание статуса. Поле lock_enabled указывает, включена ли блокировка.

GET /api/door/logs

Возвращает массив событий с полями timestamp и event. Новые события должны располагаться в начале массива.

POST /api/door/command

Принимает JSON с полями action и lock_enabled.

Поле action поддерживает следующие значения: open, close, lock_on, lock_off.

Поле lock_enabled имеет логическое значение и по умолчанию равно false.

Команда open запускает открытие ворот, если блокировка выключена.

Если блокировка включена, попытка открыть ворота должна быть отклонена. Сервер записывает соответствующее событие в журнал и возвращает HTTP 423 с сообщением «Дверь заблокирована».

Команда close запускает закрытие ворот.

Команда lock_on включает блокировку и записывает событие в журнал.

Команда lock_off отключает блокировку и записывает событие в журнал.

Для команд блокировки явное значение action является определяющим. Для команд открытия и закрытия сервер синхронизирует состояние блокировки со значением lock_enabled, полученным в запросе.

Успешная обработка команды должна возвращать HTTP 204 No Content.

4. Эмуляция GPIO

Реализуй дополнительный эндпоинт POST /api/gpio/signal для эмуляции входного GPIO-сигнала.

Эндпоинт принимает JSON с полем value, которое должно быть равно 0 или 1. Дополнительно может передаваться поле action, по умолчанию равное open.

Если value равно 1, сервер рассматривает сигнал как попытку ручного открытия ворот.

Если блокировка выключена, попытка принимается, соответствующее событие записывается в журнал, и запускается открытие ворот. Если action равно close, вместо открытия запускается закрытие.

Если блокировка включена, попытка ручного открытия отклоняется. Сервер записывает событие о недопустимой попытке и возвращает JSON с полями accepted, reason и gpio_value. Значение accepted должно быть false, а reason — locked.

При принятом сигнале сервер возвращает JSON с полями accepted и gpio_value.

Если value не равно 0 или 1, возвращается HTTP 422.

5. Эмуляция GPIO с помощью терминала

При запуске сервера необходимо запускать отдельный фоновый поток, который читает команды из интерактивного терминала. Этот поток не должен блокировать работу REST API.

Поддерживай следующие команды:

o — ручная попытка открыть ворота с учётом блокировки.

c — физическая команда закрыть ворота.

r — генерация случайного сигнала GPIO со значением 0 или 1.

0 — подать сигнал GPIO со значением 0.

1 — подать сигнал GPIO со значением 1 и выполнить попытку ручного открытия.

q — завершить только поток чтения клавиатуры. Сам HTTP-сервер должен продолжить работу.

Если терминальный ввод недоступен, API и эндпоинт /api/gpio/signal должны продолжать работать.

6. Журнал событий

Реализуй журнал событий с полями timestamp и event.

Временная метка должна содержать дату, время и часовой пояс в формате ISO 8601 с точностью до секунд.

События должны храниться в оперативной памяти в виде очереди с максимальным количеством 500 записей. Новые события добавляются в начало журнала.

Дополнительно сохраняй события в файл door_events.jsonl в папке сервера. Каждое событие записывай отдельной строкой в формате JSON с сохранением русских символов.

При запуске сервера загружай существующие записи из файла журнала, используя не более последних 500 строк. Некорректные JSON-строки пропускай.

Ошибки чтения и записи файла должны обрабатываться без аварийного завершения сервера. При ошибке записи выводи предупреждение в консоль.

Записывай события о запуске и остановке сервера, изменениях состояния ворот, командах открытия и закрытия, включении и отключении блокировки, сигналах GPIO и недопустимых попытках открытия.

7. Обработка движения ворот

Для завершения движения используй монотонные часы, чтобы корректно измерять прошедшее время.

При достижении четырёх секунд сервер должен переводить ворота в целевое состояние, очищать информацию о текущем движении и записывать событие о новом состоянии.

Если поступает команда открыть уже открытые ворота или закрыть уже закрытые ворота, не запускай лишнее движение. Запиши соответствующее событие в журнал.

8. Настройка и запуск

Подготовь README.md с инструкциями по созданию виртуального окружения, установке зависимостей и запуску сервера на Linux/macOS и Windows PowerShell.

Документация должна объяснять, что API доступен по адресу http://127.0.0.1:8000/docs.

Также опиши подключение Android-клиента: для стандартного Android-эмулятора обычно используется адрес http://10.0.2.2:8000/, а для физического телефона — IP-адрес компьютера с сервером и порт 8000. При запуске сервера в виртуальной машине необходимо учитывать сетевые настройки и правила firewall.

9. Требования к результату

Предоставь полный исходный код main.py, содержимое requirements.txt и README.md с инструкциями по установке и запуску.

Не ограничивайся фрагментами кода или псевдокодом.

Не добавляй базы данных, авторизацию, регистрацию пользователей, WebSocket, физические GPIO-библиотеки, веб-интерфейс, дополнительные эндпоинты управления или другие функции, не предусмотренные этим описанием.

Результат должен соответствовать указанному контракту REST API и быть совместимым с существующим Android-клиентом GarageControl.

Сервер должен запускаться указанной командой, корректно обрабатывать команды ворот и блокировки, возвращать состояния и журнал событий, поддерживать терминальную и HTTP-эмуляцию GPIO и сохранять историю событий в файл.
